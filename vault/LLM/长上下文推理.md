# 长上下文推理(KV 驱逐与压缩)

> [!abstract] 一句话
> 上下文越长,KV Cache 随 $n$ 线性涨(70B 单 token ≈2.6MB,128k→332GB)→ 显存/带宽双爆。解法分四类:**压缩字节、驱逐无用、结构封顶、选择保留**。主线见 [大模型推理与部署](./大模型推理与部署.md) §III.4。

---

## 1. 问题量化
KV 显存 $=2Lnh_{KV}d_h b_{kv}B$,与 $n$ **线性**且无法靠算法降阶 → 长上下文必须"少存 / 存别处"。Decode 还要每步读全量 KV,带宽同样线性恶化。

## 2. 四类解法
| 类别 | 代表 | 机理 |
|---|---|---|
| **压缩字节** | KV 量化、MLA、YOCO | 每 token 占用更少 |
| **驱逐** | H2O、StreamingLLM | 丢弃低贡献 KV |
| **结构封顶** | 滑窗注意力 | KV 永不超过 W |
| **选择保留** | SnapKV | prompt 阶段挑重要 KV |

## 3. 关键方法

### 3.1 StreamingLLM —— attention sink
**观察**:序列**最前面几个 token**吸走异常多注意力(softmax 必须把权重放某处,初始 token 成"垃圾桶")。直接滑窗丢掉它们 → 困惑度爆炸。
**做法**:保留 **4 个 sink token + 最近 W 个**,KV 定长 → **无限流式**生成不崩,无需微调。

### 3.2 H2O(Heavy-Hitter Oracle)
累计注意力分数高的 token 是"重击者",对输出贡献大。**保留重击者 + 最近窗口**,驱逐其余 → 固定 KV 预算下保质量。

### 3.3 SnapKV
**prompt 阶段**用一个观察窗统计各历史 token 被关注度,聚类选出重要 KV 压缩存储 → 长 prompt 场景(摘要/RAG)显存大降。

### 3.4 滑窗注意力(Sliding Window,Mistral)
每 token 只看最近 $W$ 个 → **KV 结构上封顶 $W$**。感受野随层数累积($L$ 层 ≈ $L\times W$),远距离信息靠层间逐跳传递。

### 3.5 结构级:MLA / YOCO
- **MLA**(DeepSeek):KV 低秩压成 latent,见 [注意力机制](./注意力机制.md)。
- **YOCO**(You Only Cache Once):跨层共享一份全局 KV,只算一次,层间复用。

## 4. 评估:大海捞针
**Needle-in-a-Haystack**:在长文随机位置埋一句话,问模型能否检索 → 检验 KV 驱逐/压缩是否丢了关键信息。驱逐类方法在"精确检索"上风险最大(可能驱逐掉"针")。

## 5. 与外推的关系
长上下文 = **位置外推(RoPE/NTK,见 [RoPE 数学推导](./题型精讲/RoPE 数学推导.md))** + **KV 管理(本篇)** 两件事,缺一不可:前者让模型"算得对",后者让显存"装得下"。
