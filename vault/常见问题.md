1. 修复后首轮请求已经带上 `business_completion_conditions`，这部分缺口确认解决。新的阻断是 Gateway 作者ing contract：模型把 `operationKind` 写成了 `navigate.launch_app`，而网关只接受 `navigate` / `send_message` / `verify` 等操作类型；同时 `successCriteria` 为空。我要在 OpenAI 工具适配层兜底：用 `requiredSemanticCode` 统一补 `metadata.semanticCode`，把 semantic 映射成合法 `operationKind`，并给首个 operation 补最小 successCriteria。
2. 是，这里主要已经不是 OpenAI prompt 问题，而是 Gateway 证据模型和 AutoGLM 证据暴露之间的问题。严格的初衷是对的，但这次 `navigate.open_search` 的处理过严，导致真实可见状态没有被承认为业务 trace。

是的，这轮具体卡点就是 Gateway 证据判定问题。

AutoGLM 日志里已经出现了“当前在 X/Twitter”“顶部显示 OpenAI AGI safety evals”“提示搜索用户、话题或关键词”“搜索页面已经可见”，但 Gateway 没有发 `search_opened`，因为它当前不把 `step.model.thinking`、`task.log`、`finish(message=...)` 当强证据。这个设计是为了防止模型自说自话，尤其是发评论、私信、下单这类副作用场景不能只凭模型日志判成功。

但对 `navigate.open_search` 这种低风险、只读/导航类动作，现在确实太保守了。


是的，**这里 Gateway 有问题，但不是“Gateway 太严格”这么简单**。更准确地说，这是一个 **证据合同不匹配 + 续跑策略过刚性 + operationId 覆盖** 的组合问题。

所以 Gateway 没有错在“不相信 AutoGLM 一句话”。它错在：

1. **没有把 AutoGLM 的弱证据记录进 continuation record**；
2. **没有给重复缺失 trace 的情况设置降级路径**；
3. **重复 semantic 使用同一个 `operationId`，导致多次尝试被覆盖**；
4. **planner 把 `search_opened` 缺失解释成“必须继续 open_search”，而不是“证据不足但可推进”。**
