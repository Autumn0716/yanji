# 操作系统概述

对应 **OS-1.1～OS-1.10**。[考纲拆分](../../../brain/research/408-syllabus/operating-systems.md)。

## 基本概念（OS-1.1）

操作系统：管理硬件与软件资源、向上提供服务的系统软件。目标：方便性、有效性、可扩展、开放性。

**特征**：并发、共享、虚拟、异步。

**功能**：处理机、存储器、文件、设备管理；用户接口（命令/GUI/系统调用）。

## 发展历程（OS-1.2）

手工操作 → 单道/多道批处理 → 分时 → 实时 → 网络/分布式/个人/嵌入式/手机 OS 等。分类可按交互、实时性、用户数等。

## 程序运行环境

### CPU 运行模式（OS-1.3）

内核态（管态）可执行特权指令；用户态（目态）不可。通过中断/异常/陷阱进入内核。

| 切换方向 | 谁完成 | 要点 |
| --- | --- | --- |
| **用户态 → 内核态** | **硬件** | 响应中断/异常/陷阱时，随中断隐指令一并改模式（常改 PSW/状态字中的态位）；软件不能自行「提权」 |
| 内核态 → 用户态 | 特权返回（如中断返回指令） | 由内核执行返回指令，硬件配合恢复 PSW/PC |

> [!IMPORTANT]
> **切入内核态由硬件完成**——不能靠用户程序一条普通指令把态改成内核态。与现场保护对照：PC/PSW（含态位）由隐指令保存/切换，通用寄存器由 OS 保存（见 [输入输出·中断](../计算机组成原理/输入输出/输入输出.md)）。

### 中断和异常（OS-1.4）

- **中断（外中断 / 硬中断）**：外设等**异步**事件
- **异常**：指令执行中的**同步**故障/陷入（如缺页、溢出）
- **软中断（软件中断 / 内中断）**：由 CPU **执行某条指令**主动引发（如 `INT`、陷阱/`syscall`）；相对外中断而言

| | 外中断（硬） | 软中断 / 内中断 |
| --- | --- | --- |
| 谁触发 | 外设等 | 指令本身 |
| 时机 | **异步** | **同步**（执行到该指令时） |
| 典型用途 | I/O 就绪、时钟 | **系统调用**、断点调试 |

> [!TIP]
> 408 主干术语常写「**中断（外）** vs **异常/陷入（内）**」；系统调用经**陷阱指令陷入**，属内中断一侧。勿与 Linux **softirq**（中断下半部）混淆；信号说「软中断式」只是类比（见 [进程管理](./进程管理.md)）。

处理：保存现场 → 判类型 → 服务例程 → 恢复。与计组交叉：外部中断时 **PC/PSW 由中断隐指令自动保存，通用寄存器由 OS 保存**；**中断向量表以数组存入口**，便于 CPU 按下标最快取处理入口、保障响应瞬时性（见 [输入输出·中断向量表](../计算机组成原理/输入输出/输入输出.md)、[流水线与异常](../计算机组成原理/CPU/流水线与异常.md)）。

### 系统调用（OS-1.5）

用户态请求内核服务的接口；经陷阱指令陷入。分类：进程、文件、设备、信息维护等。区别于库函数（库可在用户态，最终常包一层系统调用）。

### 链接与装入（OS-1.6）

- 链接：静态 / 动态（装入时或运行时）
- 装入：绝对、可重定位、动态运行装入

### 内存映像与地址空间（OS-1.7）

典型用户进程：代码段、数据段、堆（向上长）、栈（向下长）；逻辑地址空间视图。

## 操作系统结构（OS-1.8）

| 结构 | 要点 |
| --- | --- |
| 模块化 | 功能模块，接口调用（高内聚、低耦合）；考题常挂 **灵活、易扩展/维护** |
| 分层 | **单向依赖**（只调下层）；**结构清晰、便于调试 / 易保证正确性** |
| 宏内核 | 多数服务在内核，**性能好**、耦合高 |
| 微内核 | 内核极薄，服务用户态，消息通信，**可靠**/可移植 |
| 外核 | 尽量把抽象下放到库，硬件安全复用 |



### 易混：分层 vs 模块化

| | 分层 | 模块化 |
| --- | --- | --- |
| 依赖 | **单向**，层次清楚 | 经接口互调，依赖可成**网状** |
| 考题常挂的优点 | **结构清晰、便于调试 / 易保证正确性**（自底向上逐层验证） | **灵活、易扩展**（高内聚、低耦合） |
| 代价 | 层多可能损效率、欠灵活 | 调用一乱则并不「清晰好调」 |

> [!TIP]
>
> 「用……设计的 OS **结构清晰且便于调试**」→ 填 **分层**，不是模块化。



### 模块化

内核中模块之间是相互依赖的,某个功能往往依赖于另一个功能的实现,因此如果其中有一个模块故障时往往会影响整个内核的稳定性,模块化是更难于调试和验证的

***可靠性&#x20;*要靠微内核提供**

*性能好&#x20;*要靠宏内核提供(因为大多数功能都在用户态,尽可能不会影响内核)



### 微内核

可靠性好,但是*性能不佳*,因为总需要**内核态和用户态**之间进行频繁切换

1. 面向对象(每个服务都是一个对象)
2. 内核足够小
3. 采用C-S模型,客户-服务器
4. 策略与机制分离(策略在用户态,机制在内核态)

微内核的每个服务都作为一个客户端,请求给内核层

<Callout type="tip" collapsible={false} defaultOpen>
  微内核适合放入的服务:

  1. 进程间的通信
  2. 低级IO
  3. 低级进程管理和调度
  4. 中断和陷入处理

  但是!**文件服务系统**是交给微内核之外的文件系统服务器,==**不适合**==放入微内核里
</Callout>

微内核的性能不佳,因为要经常做用户态-内核态的切换

操作系统执行开销比较大



#NB 微内核的性能不好,不存在"使整个系统更加高效"



微内核的安全性也比宏内核高,存在"故障隔离"

即安全隔离,

在微内核中,不同进程之间不能直接访问对方的内存,必须通过IPC实现消息传递,

<Callout type="note" collapsible={false} defaultOpen>
  Windows是融合宏内核和微内核的系统
</Callout>

## 引导（OS-1.9）

加电自检 → 固件（BIOS/UEFI）→ 引导加载程序 → 装入内核 → 初始化 → 用户态第一个进程。

<Callout type="tip" collapsible={false} defaultOpen>
  存放操作系统自举程序的芯片是ROM
</Callout>

BIOS只可读(部分也可写)



**引导程序分为两部分:**

**一种位于ROM中的自举系统**

**另一种位于操作系统硬盘的引导扇区中的引导程序**



<Callout type="note" collapsible={false} defaultOpen>
  计算机的启动过程:

  1. CPU加电,从顶端地址FFFF0H获得第一条指令执行,
  2. 16字节地址放不下一段程序,JMP跳到BIOS
  3. BIOS在内存最开始空间构建中断向量表和相应服务程序
  4. 通电自检POST(Power-on Self Test)
  5. POST之后BIOS需要在硬盘,光驱或者软驱操作系统内核的位置启动操作系统
</Callout>

MBR(Main Boot Record)主引导记录

BIOS交给启动设备后,CPU把主引导扇区的内容加载到内存,MBR检查分区表,引导扇区加载到内存并执行



## 虚拟机（OS-1.10）

在软硬件接口上虚拟完整机器。类型 I（裸金属）/ 类型 II（宿主 OS 上）——深度 `uncertain`。

虚拟机本质上就是一个应用程序,并不是真正的并行



**第一类VMM**直接于行在硬件上

**第二类VMM**在宿主操作系统上,不能直接和硬件打交道

因此**从效率上:第一类VMM>第二类VMM**

VMM的功能没有操作系统复杂,因此代码远低于真实操作系统



第一类VMM存运行在内核态

第二类VMM是用户态
