# 显示器、色深与显存

> [!abstract] 一句话
> 显示器把帧缓冲里的像素「刷」到屏幕上；**色深**管精度，**色域**管范围；CRT/LCD 比「快」看冲激还是保持；**显存/带宽**管装得下、送得动。

与 [输入输出系统](输入输出.md) 的关系：显示是典型高速输出设备——帧缓冲在 **VRAM（显存）**，经显示控制器/GPU 按时序刷新；数据通路直觉接近「成批搬像素」，常走专用显存与显示链路，而非 CPU 逐像素轮询。

溯源：[Color depth](../../../../brain/external-sources/color-depth-wikipedia.md)、[Rec. 2020](../../../../brain/external-sources/rec-2020-wikipedia.md)、[CRT](../../../../brain/external-sources/crt-wikipedia.md)、[字体光栅化](../../../../brain/external-sources/font-rasterization-wikipedia.md)。

## 1. 色深（color depth）

每个像素用多少 **bit** 表示颜色（也常说每分量 bpc）：

$$
\text{可区分码值数} = 2^{\text{色深（bpp）}}
$$

| 色深 | 俗称 | 直觉 |
| --- | --- | --- |
| 1 bit | 黑白 | 2 色 |
| 8 bit | 索引色 / 256 色 | 常查调色板 |
| 15/16 bit | High color | 约 3.2万～6.5万色 |
| **24 bit** | **真彩 True color** | R/G/B 各 8 bit，约 **1677 万**色 |
| 32 bit | 真彩 + Alpha | 颜色仍常是 24 bit，多 8 bit 透明度 |
| ≥30 bit（如 10 bpc） | Deep color | 梯度更细，HDR/宽色域常用 |

> [!TIP]
> **真彩 ≠「世界上所有颜色」**，而是：在当前色域里，24-bit 分得够细、看起来接近连续。见 [色深备忘](../../../../brain/external-sources/color-depth-wikipedia.md)。

## 2. 色域：RGB、P3、Rec.2020

- **RGB** 是加色模型（三原色相加混色），**不是**某一种固定色域。
- 日常说的「普通 RGB」多半指 **sRGB / Rec.709**。
- **Display P3 / DCI-P3**、**Rec.2020** 也是 RGB，只是原色更「纯」、三角形更大。

覆盖人眼可见色（CIE 1931 面积，约数，见 [Rec.2020 备忘](../../../../brain/external-sources/rec-2020-wikipedia.md)）：

| 色空间 | 约覆盖可见色 |
| --- | --- |
| Rec.709 / sRGB | **35.9%** |
| DCI-P3（与 Display P3 原色同族） | **53.6%** |
| Rec.2020 | **75.8%** |

```mermaid
graph LR
  eye["人眼可见色域"]
  r709["sRGB / Rec.709 ≈36%"]
  p3["P3 ≈54%"]
  r2020["Rec.2020 ≈76%"]
  eye --> r2020
  r2020 --> p3
  p3 --> r709
```

要点：

- **Display P3 不够「全部颜色」**——大约只到可见色的一半。
- **Rec.2020 仍是 RGB**，原色接近单色激光（630 / 532 / 467 nm）；比 sRGB 色域面积大约 **2 倍+**。
- 三原色在色度图上永远是**三角形**，盖不满弯曲的马蹄形可见区 → **没有普通三原色屏能显示人眼可见的 100%**。再往上靠多原色或光谱级再现。

## 3. CRT（阴极射线管）与 LCD：谁「更快」？

Cathode Ray Tube

溯源：[CRT Wikipedia 备忘](../../../../brain/external-sources/crt-wikipedia.md)、[CRT vs LCD 运动清晰度](../../../../brain/external-sources/crt-vs-lcd-blurbusters.md)。

### 3.1 CRT 怎么工作

```mermaid
flowchart LR
  gun[电子枪] --> beam[电子束]
  beam --> def[偏转线圈]
  def --> mask[荫罩]
  mask --> phos[荧光粉发光]
```

| 部件 | 作用 |
| --- | --- |
| 电子枪 | 加热阴极发射电子，调制束流强弱（亮度） |
| 聚焦 / 偏转 | 把束对准屏幕上的目标点；显示器多为磁偏转 |
| 荫罩（彩色） | 让 R/G/B 三束分别打到对应荧光点 |
| 荧光粉 | 被电子打中后发光，随后衰减 |
| 光栅扫描 | 按固定图案逐行扫完整帧（可逐行或隔行） |

一帧不是「整屏同时亮着」，而是电子束扫到哪亮哪；荧光粉衰减后该点变暗，直到下一帧再扫到。

### 3.2 比 LCD 快吗？

要先分清「快」指什么：

| 含义 | CRT | 普通 LCD |
| --- | --- | --- |
| 像素状态切换 | 荧光粉约毫秒级衰减（示例约 1-2 ms） | 液晶扭转；早期较慢，现代 GtG 也可到约 1 ms 量级 |
| 运动清晰度 | 冲激式（impulse）：每帧短暂闪光，多数时间偏暗 | 采样保持（sample-and-hold）：整帧持续点亮，眼动追踪时易感知拖影 |
| 刷新率标称 | 常见 60-85 Hz+，高刷 CRT 有，但体积功耗大 | 现代游戏屏常 144-360 Hz，数字更高 |
| 输入延迟体感 | 历史上常优于早期 LCD | 现代高刷 + 低延迟面板已大幅追平 |

> [!IMPORTANT]
> 运动上看，CRT 往往比「同刷新率的普通 LCD」更清晰——不是因为刷新率数字更大，而是发光方式不同（冲激 vs 保持）。早期 LCD 拖影明显时，大家会说 CRT「更快」；这主要指运动响应/清晰度，不是分辨率或色域。

补充：

- 现代 LCD 用频闪背光（ULMB 等）可模仿 CRT 冲激，接近其运动清晰度，但常牺牲亮度或引入闪烁。
- OLED 像素开关极快，运动表现通常优于传统 LCD，仍属保持型显示（可再加黑帧/频闪策略）。
- CRT 短处：笨重、耗电、几何失真、闪烁疲劳、难做超大超薄——所以被平板取代。

408 记忆钩：CRT = 扫描电子束 + 荧光粉；LCD = 背光 + 液晶阀。比「快」时优先想冲激 vs 采样保持。

## 4. 字符显示：点阵、锯齿与现代解法

溯源：[Font rasterization Wikipedia 备忘](../../../../brain/external-sources/font-rasterization-wikipedia.md)。

### 4.1 你的直觉对不对？

**对。** 屏幕最终只能点亮离散像素；字符要变成「亮/暗（或彩色）点阵」。

早期硬件常见做法：

- **字模 ROM / 字符发生器**：每个字符存成固定大小的点阵（如 8×8、8×16），1 = 亮点，0 = 暗点
- 文本模式：显存里只存字符码 + 属性，由硬件查表画出字形

像素相对笔画很「稀」时，斜线/圆弧只能用阶梯近似 → **锯齿（jaggies / aliasing）**。

### 4.2 锯齿怎么缓解？

| 手段 | 在干什么 |
| --- | --- |
| **提高像素密度（PPI）** | 同样物理笔画占更多像素，阶梯更细，肉眼难看出来 |
| **矢量字 + 实时光栅化** | TrueType/OpenType 存轮廓曲线，按当前字号栅格化，不再绑死某一分辨率的死点阵 |
| **抗锯齿（AA）** | 边缘像素按覆盖比例填灰度（不完全黑/白），视觉上抹平锯齿 |
| **字体 hinting** | 提示光栅器把竖线/横线尽量对齐像素格，小字号更清楚 |
| **次像素渲染** | 利用 R/G/B 子像素做更细的水平采样（如 ClearType），有效分辨率更高 |

> [!TIP]
> 408/计组记两层：底层仍是「像素网格」；上层用矢量 + AA/次像素，避免「只靠固定低分辨率字模」。

### 4.3 现在的显示器还是老技术吗？

**一半一半：**

| 层 | 现在 |
| --- | --- |
| 显示器件 | 仍是**离散像素阵**（LCD/OLED 等），本质还是光栅，不是无限连续纸面 |
| 文字管线 | 一般**不再**靠显卡里那套固定字模 ROM 做桌面 UI；OS/GPU 把矢量字光栅化进帧缓冲 |
| 特例 | 终端点阵字体、嵌入式小屏、BIOS/早期文本模式仍可能用纯点阵字 |

所以：锯齿问题没「物理消失」，是被 **更高 PPI + 矢量字形 + 抗锯齿/次像素** 压到多数场景不刺眼；把屏幕放大或字号极小，仍可能看见阶梯或 AA 发糊。

## 5. 显存（VRAM）要装什么

**VRAM**：GPU/显示子系统的本地存储器，典型用途：

| 内容 | 作用 |
| --- | --- |
| **帧缓冲（framebuffer）** | 当前（及后缓冲）整屏像素 |
| 纹理 / 渲染目标 | 3D、合成、后处理 |
| 其他 GPU 工作集 | 几何、计算缓冲等 |

### 单帧缓冲容量（下限直觉）

$$
\text{帧缓冲字节数} \approx W \times H \times \frac{\text{色深（bit）}}{8}
$$

例（未计多缓冲、对齐、压缩）：

| 分辨率 | 色深 | 约占用 |
| --- | --- | --- |
| 1920×1080 | 24-bit | ≈ 6.2 MB |
| 1920×1080 | 32-bit | ≈ 8.3 MB |
| 3840×2160 | 32-bit | ≈ 33 MB |

双缓冲 / 三缓冲、MSAA、纹理会把实际占用抬高许多；游戏显卡的「8 GB VRAM」远不止一张桌面。

> [!NOTE]
> 408 常考的是：**分辨率 ↑ 或色深 ↑ → 显存需求 ↑（近似成正比）**。

---

> [!QUESTION] 那为什么游戏显卡动辄 16 GB？一张 4K 帧缓冲才 33 MB
> 因为 VRAM 装的不是「一帧」，而是**整条渲染流水线的工作集**，帧缓冲只是其中一小块：
>
> - **纹理（最大头，常占 50%–70%+）**：一个场景几百到上千张贴图（albedo / normal / roughness / metallic / AO…），4K 贴图单张十几 MB，合计数 GB～十几 GB
> - **渲染目标 / G-buffer**：延迟渲染同时持有 albedo、normal、depth、material 等多张全屏 HDR 缓冲，4K 下一套几百 MB
> - **阴影图 / 后处理缓冲**：级联阴影多张高分辨率深度图；bloom、SSR、motion blur 各需中间缓冲
> - **多缓冲 / MSAA**：双/三缓冲 × 帧缓冲；MSAA 按采样数倍增
> - **几何 / BVH / 着色器 / AI 权重**：顶点数据、光线追踪加速结构、跑 LLM 时的模型权重等
>
> 一句话：**帧缓冲是「最终交付的那一张」，VRAM 是「整条流水线的车间」**。这也是「降材质画质能省显存」的根源。

## 6. 显存带宽与刷新带宽

两件不同的事，别混：

### 6.1 扫屏最低带宽（像素出屏）

要把一帧按时送到面板，粗算：

$$
\text{像素带宽} \approx W \times H \times \text{色深（bit）} \times \text{刷新率}
$$

例：1080p60、24 bpp（未计消隐、链路编码开销）：

$$
1920 \times 1080 \times 24 \times 60 = 2\,985\,984\,000\ \mathrm{bit/s} \approx 2.99\ \mathrm{Gbit/s}
$$

口算量级记 **≈ 3 Gbit/s**。分辨率、色深、刷新率任一翻倍，需求大致翻倍。

### 6.2 显存接口带宽（GPU ↔ VRAM）

GPU 还要读写纹理、渲染目标等，**显存带宽**通常远高于「仅扫屏」：

$$
\text{显存带宽} \approx \text{总线位宽} \times \text{有效数据速率}
$$

（GDDR 等还会乘「每时钟传输次数」等因子；看规格表给的 GB/s 即可。）

| 瓶颈体感 | 现象 |
| --- | --- |
| VRAM **容量**不够 | 卡顿、降材质、爆显存 |
| VRAM **带宽**不够 | 高分辨率/高刷下帧率掉、填充满 |
| 显示链路带宽不够 | 无法开到目标分辨率×色深×刷新（需压缩或降规格） |

与总线关系见 [总线](../总线/总线.md)（高速图形常挂系统/扩展总线一侧）。

---

> [!TIP] 为什么显存带宽（数百 GB/s）远高于扫屏带宽（几 GB/s）？
> 扫屏只把**最终一帧**送出一次；而渲染这一帧时，GPU 要把每张贴图、每个渲染目标**反复读写很多遍**（Z-prepass、G-buffer、光照、阴影、后处理…）。一帧内部搬运量是最终帧缓冲的几十到上百倍，60 FPS 累加就是数百 GB/s--这正是 RTX 4090 ≈ 1008 GB/s 的来由。

## 7. 和 I/O 控制方式的对照（记忆钩）

| | 直觉 |
| --- | --- |
| 早期简单显示 | CPU/控制器写显存单元，类似程序控制 |
| 现代 GPU | 大批量 DMA 式搬数据 + 本地 VRAM 计算 |
| 刷新 | 显示控制器按行场时序读出帧缓冲（持续「输出」） |

细节控制方式仍回到 [输入输出系统](输入输出.md)。
